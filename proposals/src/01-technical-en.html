1 Executive summary

What is required is not a directory of tradespeople, nor a classified-ads platform, but a complete service operations and management platform — beginning with a customer's need and ending with a financial report. That understanding shaped every engineering decision in this document.

We read the requirements specification in full, across all thirty-two of its sections, and built an interactive prototype of the customer journey which was approved visually before this proposal was written. Our conclusion is that the success of AWNAK rests on four engineering pillars, not on a screen count:

Service categories that flex without code
The specification states explicitly that the operator must be able to add new categories and services without any programming change. The catalogue is therefore built on a dynamic field schema defined from the admin panel, not on fixed tables per trade.
A dispatch engine, not a search list
An order is not merely published — it is routed against ten criteria: specialisation, location, coverage radius, rating, response speed and availability. That is a scoring engine whose weights are tunable from the panel.
A ledger, not a "price" field
Held funds, multi-rule commission, additional costs, partial refunds and provider balances all require double-entry bookkeeping. Anything less makes the balances impossible to audit later.
Arabic-first, not translated
Native RTL layout, search that tolerates variant spellings of hamza and taa marbuta, grammatical gender that follows the account, and type sizing that respects older users — handled in the search layer and the interface together.

1.2 A foundational architectural decision

One account, two modes — not two accounts As the specification requires, identity (User) is separated from the professional profile (Provider Profile) in the data model. A user remains a single user and a professional profile is attached after verification. This prevents duplicated records, makes switching between customer mode and provider mode instantaneous without signing out, and keeps order history and ratings tied to one identity.

3.1 The replaceable adapter principle

Every external integration sits behind a single internal interface. Changing the SMS provider or adding a second payment gateway requires writing a new adapter only, not editing business logic — which serves the "ability to add new payment gateways" requirement directly, and protects the project from being locked to any one vendor.

3.2 Why a modular core rather than microservices

CriterionDecision and reasoning
Financial transaction integrity Holding funds, deducting commission and releasing the provider's balance must occur in a single atomic transaction. Splitting this across microservices imposes complex and risky distributed transactions on a financial system.
Team size and delivery time Microservices impose an infrastructure overhead that consumes phase-one budget without delivering value before a large user base exists.
Separability later Modules are separated by clear boundaries and internal interfaces, so any module — messaging or notifications, for example — can be extracted as a standalone service when needed, without a rewrite.
Horizontal scaling The core is stateless and runs as multiple instances behind a load balancer; asynchronous workers scale independently of the API.

5 Data model and database

A normalised model that separates identity from the professional profile from the financial entry. That separation is what allows one account with two modes, sound financial auditing, and adding new services without a code change.

5.2 The architectural key — dynamic service fields

The hardest requirement in the specification is that the operator can add new services without a programming change. The answer is to define each service's order form as data:

Field definition
For each service the operator defines its fields: type (text, number, choice, image, date), whether it is mandatory, its permitted values, and display order.
Automatic rendering
The app builds the order screen from that definition at runtime, so a new service appears with the correct form without an app store update.
Flexible but indexed
Answers are stored in an indexed JSONB column, so they remain searchable, filterable and reportable despite the flexibility.
What this means in practice Adding a new trade — "curtains and upholstery technician", say — with its own fields, pricing model, required documents, commission and coverage areas is done from the admin panel in minutes, with no new app release and no waiting for store review.

5.3 Data policies

  • Soft deletion for every record tied to a financial transaction or a dispute, to preserve auditability.
  • Column-level encryption for identity numbers and financial data.
  • Document isolation in dedicated storage behind short-lived signed URLs, reachable only by an authorised staff member, with every access recorded in the audit log.
  • Deletion on request under the privacy policy, anonymising financial entries rather than deleting them, so the books stay sound.

6 Matching and dispatch engine

The specification sets out ten criteria for dispatching an order. We implement them as a scoring engine whose weights are tunable from the admin panel, not fixed in code.

6.1 Engine stages

1
Hard filtering
Accounts failing a mandatory condition are excluded outright: mismatched specialisation, location outside the coverage radius, unverified or suspended account, outside declared working hours, or availability toggled off. This runs as a single PostGIS query against a spatial index.
2
Weighted scoring
Each remaining candidate is scored against the soft criteria in the table below. Weights are set from the panel and tested before being adopted.
3
Staged fan-out
The order goes first to the highest-scoring tier; if not enough quotes arrive within a set window, the circle widens automatically. This rewards the best performers without leaving a customer's order without quotes.
4
Throttling
A cap on orders sent to a provider per period, and a cap on quotes per order — protecting quote quality and the customer's experience.
5
Verification and subscription gating
Verification tier and subscription plan affect priority and the monthly quota of quotes, supporting the revenue model later without a code change.

6.2 Scoring criteria and default weights

CriterionInitial weightHow it is calculated
Geographic proximity20%Linear decay with distance within the declared coverage radius.
Overall rating20%Weighted average giving greater weight to recent ratings.
Response speed15%Median time from order receipt to quote submission over the last thirty days.
Completed orders12%Logarithmic scaling to prevent incumbents monopolising dispatch.
Verification tier12%Registered ‹ verified ‹ verified company.
Order acceptance rate8%Accepted ÷ dispatched, above a minimum sample size.
Punctuality7%Share of arrivals within the quoted arrival window.
Availability at the requested time6%Declared schedule against the requested service time.
Years of experience6%A supporting factor with a defined ceiling.
Cancellation rate−6%A penalty for provider-side cancellations.

These weights are initial and will be confirmed with the project owner during the analysis phase. They remain adjustable from the admin panel at any time without a new release.

An explicit requirement, addressed The specification warns that subjecting every order to manual approval delays urgent work. An order is therefore published automatically once it passes automated checks — data completeness, location validity, prohibited content screening, banned keywords, duplicate detection and account eligibility — and only what the rules classify as suspicious is routed to manual review.

7 Order lifecycle and pricing models

7.1 The order state machine

The fifteen states are implemented as an explicit state machine: every transition has a condition and an authorised actor, and is recorded in order_status_history. Disallowed transitions are rejected at the system level, not merely hidden in the interface.

New orderAwaiting quotes Quotes receivedProvider selected Awaiting payment or confirmationProvider en route Provider arrivedIn progress Awaiting customer approval of extra work Service completedAwaiting customer confirmation CompleteCancelled StalledUnder dispute Refunded in full or in part

7.2 The seven stages of an order

#StageWhat the system does
1Order creation Category and service selection, a short title, a description of the problem, photo and video attachments, service address and map location, timing (now / today / a later slot), urgency level, an optional indicative budget, and preferred payment method.
2Order screening Automated checks on data completeness, location validity, service type, prohibited content, banned keywords, duplicates and account eligibility. Publication is automatic; only suspicious orders go to manual review.
3Dispatch The matching engine (section 6) routes the order across staged tiers.
4Quotes Proposed price, labour charges, materials cost, duration, expected arrival time, quote validity period, conditions, notes and attachments.
5Selection The customer compares quotes — name, photo, verification badge, rating, jobs completed, experience, price, arrival time, duration. On selection, quoting closes, the chosen provider is notified, and the others are told the competition has ended.
6Execution State progression, additional work or materials only with prior customer approval, and live status updates on both sides.
7Completion The provider marks the service complete and uploads after photos; the customer is notified and confirms; commission is deducted and the balance released; both parties are asked to rate. If the customer does not respond within a window set by the operator, the order closes automatically after a status review.

7.3 The six pricing models

The specification notes that services cannot all be priced the same way. Each model is implemented as an independent strategy, bound to a service from the admin panel:

ModelUsed forBehaviour in the system
Fixed priceTyre inflation, tyre change, air-conditioner cleaning, light fitting, car wash, inspection visit. The base price is shown before ordering; the quoting stage is skipped and the order is assigned directly.
QuotationHouse painting, furniture moving, leak repair, appliance repair, carpentry and metalwork. The full cycle: details and photos → competing quotes → selection.
InspectionWork that cannot be estimated remotely. An inspection visit fee is paid first — and deducted from the job value — then a final price is submitted after inspection and approved inside the same order.
HourlyHourly labour and open-ended work. Total = hours × number of workers × hourly rate, with start and end times recorded.
EmergencyUrgent faults. Dispatched to providers available right now within a tight radius, with an urgency surcharge set by the system or the provider under platform policy.
Direct requestOrdering from a specific provider's page, or repeating a past order. Bypasses dispatch and goes to the named provider, with the timing, address or details editable.

8 Payments, wallet and commission

The governing principle of the financial layer Every movement of money is an entry in an immutable ledger. Balances are computed from the sum of entries rather than stored in a single field, and no entry is edited after posting — corrections are made by reversing entry. This is a precondition for auditable financial reporting and for resolving disputes.

8.1 Supported payment methods

MethodPhaseNotes
Cash on completionPhase 1 Commission is posted as a debt against the provider, settled from later balances.
Electronic payment via one gatewayPhase 1 The gateway is chosen with the project owner; the integration is priced separately.
Electronic wallet and balancePhase 2 The ledger foundation ships in phase one; the user-facing surface is added later.
Escrow holdPhase 2 Detailed in 8.2; requires a gateway supporting hold and release.
Partial or full prepaymentPhase 2 Built on the wallet and the escrow hold.

8.2 The escrow cycle

1
Payment
The customer pays the service value electronically after accepting a quote.
2
Hold
The amount is posted to the platform's trust account and not transferred to the provider; it appears to them as a "held balance".
3
Confirmation
The customer confirms completion, or the order closes automatically after the defined window.
4
Settlement
Platform commission is deducted by entry and the net added to the provider's available balance by matching entry.
5
Withdrawal
The provider requests a withdrawal; the operator reviews it and the transfer is executed and posted.

8.4 Additional costs during execution

No additional work begins without the customer's explicit approval. The order moves to "Awaiting customer approval of extra work" and no increase is counted until approval. The provider adds a line with its reason and value, the customer is notified, and on approval the value is added to the order total and commission is recalculated on the new total.

19 Security and data protection

Requirement in the specificationImplementation
SSL-encrypted communicationTLS 1.3 enforced on every domain with HSTS, and certificate pinning in the app for sensitive paths.
Encryption of passwords and sensitive dataArgon2id hashing for any password, column-level encryption for sensitive fields, and disk encryption for backups.
Secure access tokensShort-lived JWTs with rotating refresh tokens and reuse detection; tokens held in the device's encrypted store.
Bounded session lengthA duration configurable from the panel, remote session termination, and active devices visible to the user.
Preventing repeated login attemptsEscalating rate limits by number, network address and device, with temporary lockout and an administrative alert.
Logging sensitive operationsAn immutable audit log for every administrative and financial action, with actor, timestamp and before/after values.
Documents hidden from unauthorised staffDocuments in dedicated storage behind short-lived signed URLs, governed by permissions, with every access recorded.
Regular backupsDaily full backups with continuous log archiving, and documented periodic restore testing.
API protectionMandatory authentication, strict input validation, per-route rate limiting, and prevention of over-fetching.
Protection against forged requestsDevice integrity checks, signing keys for sensitive requests, and automated-pattern detection.
Fine-grained staff permissionsRBAC at action and field level, with privilege-escalation prevention and separation of duties on the financial path.
Deletion or masking under the privacy policyDeletion on request, anonymising financial entries rather than deleting them so the ledger stays intact.

In addition: automated dependency scanning on every build, and a manual review of the critical paths — authentication, payments, permissions and file upload — before launch, with the findings addressed within the delivery scope.
